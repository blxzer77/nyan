# Agent Note: Bun runtime adapter parallelization

Status: implemented

Scope of "implemented": the four batches described under Decision. The gate described under Consequences closed on 2026-10-17 with PR #32, and Bun Phase 2 is Done in `ROADMAP.md`.

## Problem

Bun support is already functional, but runtime decisions are split between `config.ts`, inline `process.versions.bun` checks, the HTTP dispatcher, worker paths, source loading, subprocess setup, and the `@ny4n/ai` package. N2 is also changing the durable product path and the extension surface. Editing these areas without a fixed boundary can change the meaning of the existing Bun/Node branches or create avoidable conflicts between the two active work lines.

## Decision

Run Bun Phase 2 as the second active roadmap line alongside N2, with no more than the two lines allowed by `ROADMAP.md`.

The first Phase 2 batch establishes a pure coding-agent runtime identity module at `packages/coding-agent/src/runtime.ts`. It owns only runtime identity and detection:

- `RuntimeKind` is the string union `"bun-binary" | "bun" | "bundled-node" | "node"`.
- `isBunBinary`, `isBunRuntime`, and `isBundledNode` retain their current module-load snapshot semantics and public names.
- `runningUnderBun()` retains its current re-read semantics because tests intentionally change `process.versions.bun` after module load.
- `getRuntimeKind()` resolves with the precedence Bun binary, bundled Node, Bun, unbundled Node. Its Bun input is re-read on each call, while the Bun binary and bundled Node inputs are the load-time snapshots.

`config.ts` continues to own package paths and product configuration. It re-exports the existing identity names from `runtime.ts` so current imports remain compatible; it does not become the runtime adapter.

The first batch also centralizes the HTTP dispatcher branch on `runningUnderBun()` without changing the existing Bun-native-fetch or Node-undici policy. The second batch moves the stdout takeover branch in `packages/coding-agent/src/core/output-guard.ts` to `runningUnderBun()` and replaces the duplicated `bun/x` versus `node/x` label in `packages/coding-agent/src/utils/nyan-user-agent.ts` and `packages/coding-agent/src/core/bug-report.ts` with `getRuntimeLabel()`. `getRuntimeLabel()` re-reads `process.versions` on each call, so it keeps the same test-time behavior as the inline checks it replaces. It also keeps their truthiness test, whereas `runningUnderBun()` keeps its `typeof` test; the two differ only for an empty `process.versions.bun`, which Bun does not report, and `test/runtime.test.ts` pins that difference so changing either is a deliberate decision. The third batch gives `@ny4n/ai` its own boundary, because `ai` is a lower layer that must load in a browser bundle and cannot import coding-agent. `packages/ai/src/utils/runtime.ts` sits in the `contracts` module layer, imports nothing, and exports `isNodeLikeRuntime()` (Node or Bun, that is, not a browser) and `runningUnderBun()`. Both re-read `process.versions` on every call, so each of the eight former inline checks keeps its evaluation time and truthiness behavior. The two helpers are separate on purpose: Bun also reports `process.versions.node`, so a Bun-only branch must not be written as the Node-like check.

The fourth batch moves the remaining consumers. `bun/restore-sandbox-env.ts`, `experimental/source-runtime-args.ts`, and `utils/image-resize.ts` use `runningUnderBun()`. `experimental/process.ts`, `main.ts`, and `core/extensions/loader.ts` read `isBunBinary` and `isBundledNode` from `runtime.ts` instead of the `config.ts` re-export, which stays for other importers. `scripts/build-binaries.mjs` also resolves the Bun executable through `scripts/bun-command.mjs`. The last three of those source files (`main.ts`, `loader.ts`, `image-resize.ts`) are the files N2 reserved; they are migrated in one commit of their own so that the N2 session can recognize it when merging. In `loader.ts`, `isTypeScriptSourceRuntime` and `usesEmbeddedModules` stay load-time snapshots on purpose: `getRuntimeKind()` re-reads the Bun marker, and these two constants must not change when a test flips it. `isNodeSeaBinary` in `loader.ts` stays inline. It is not folded into `RuntimeKind`; whether Node SEA becomes a runtime kind is left for a design decision.

The N2 file reservation was explicit: the first Phase 2 batches must not modify `main.ts`, `core/extensions/loader.ts`, `core/durable/**`, `modes/durable/**`, or image/resource files that N2 may reconnect. The fourth batch edits the three reserved files only after the owner confirmed that N2 had not touched them, and `core/durable/**` and `modes/durable/**` stay untouched. Any later overlap requires a fresh reservation before editing.

## Alternatives considered

- **Keep the identity in `config.ts`:** rejected because `config.ts` imports filesystem, OS, path, package identity, and process helpers and reads `package.json` during module initialization; it is not a pure identity boundary.
- **Add one adapter abstraction for every Bun difference:** rejected because most differences are product-specific path or loading behavior, while HTTP is the only current pair of complete Node/Bun implementations. Over-abstraction would increase layering and browser risks.
- **Change the HTTP policy while extracting the identity:** rejected because Owner Decision #12 kept the Bun-native-fetch versus undici choice open. This batch only changes the source of the branch decision. The owner resolved the decision on 2026-10-17 (Bun-native fetch, behind the runtime adapter); that work is Bun Phase 3.
- **Run Phase 2 after N2:** rejected because the roadmap explicitly makes Phase 2 independent of N0/N2, and the two work lines can be kept disjoint.

## Consequences

Phase 2 gets a stable base contract and ships in four batches. The new base module requires the coding-agent architecture catalogue to include `runtime.ts`. Every inline runtime-identity consumer found in `coding-agent` and `ai` goes through `runtime.ts`, including the extension loader, `main.ts`, image resize, and the `ai` provider checks. The gate the owner set, which closed on 2026-10-17 (results under "Gate result"), was: a local `npm run check` that passes after the branch is rebased onto `main`; the targeted Node and Bun tests, including the two Node failures from the first targeted run; a green PR CI (Node and Bun full suites on Ubuntu, build and check on Windows); and a dry run of `release.yml` on the branch that builds the six binaries, their archives, and `SHA256SUMS`, and passes binary smoke with `smoke-test-binary-update.mjs`. The full Bun suite on a Windows host was not part of the gate, because CI has no Windows Bun matrix; its results are evidence for Bun Phase 3. The Linux sandbox branch of `restoreSandboxEnv()` stays unverified and did not block the gate. Outside Phase 2: subprocess and worker unification, SQLite, the HTTP policy of Owner Decision #12 (resolved, implemented in Phase 3), and whether `isNodeSeaBinary` becomes a runtime kind. N2 retains ownership of durable integration and extension/resource behavior.

- Tests added or extended: `restore-sandbox-env.test.ts` gained a case for a non-Bun runtime with an empty `process.env` (the old first case has entries in `process.env`, so the second guard returned before the Bun guard mattered, and removing the Bun guard failed nothing) and the empty-marker case. `experimental-source-runtime-args.test.ts`, `experimental-process-runtime.test.ts`, `image-resize-runtime.test.ts`, `main-binary-update-cleanup.test.ts`, and `extension-loader-runtime.test.ts` are new. Because the compiled-binary and bundled-Node flags are load-time snapshots, the process, main, and loader tests replace the runtime module with a getter that the test drives; the process test also replaces `config.ts` and `spawn`, the main test replaces the three cleanups it would otherwise run against the directory of the Node or Bun executable, and the loader test loads a fresh copy of `loader.ts` per case after `config.ts` has loaded with both flags off.
