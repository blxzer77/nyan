## N4 定稿（要记住的 6 条）

1. **掩码 = 清而不删。** 条目不可变且永不删除，被遮内容仍在库里；掩码只写"这条不要再发送"，恢复路径就是条目本身。**没有 artifact、没有 sha256、没有读盘校验。** 外部参照：Claude Code 的 `MicroCompact`（`[Old tool result content cleared]`，原内容仍在 transcript）。
2. **没有 `blocked` 状态。** 逐条检查后没有真正的产生者，因此 `nyan.live` / RPC `get_state` / `--mode json` 事件集合都不变。
3. **准入三分支**：`continue` / `mask` / `compact`。量化依据：22 个真实会话里工具结果占估算上下文 **94.9%**；只清旧结果就能把 200k 下 1→0、128k 下 3→0、64k 下 9→3 的超预算会话拉回预算内。所以 mask 是主路径，不是优化。
4. **切点 = 三条不变量**（tool 配对、在飞那一轮不切不遮、写 boundary 标记），不引入 turn 模型。
5. **来源绑定不用哈希**：`basis = { head, entryCount, tailId }`，由 `basisOf` 给出。
6. **回执写进摘要条目自己的 `data`**，不新增文档类型。

### 裁决（切片 C 必须按这个做）

- `isProtected` 的 `index` 是**条目位置**（不是切点边界）——已同意。
- `basisOf` 返回三元组——已同意；但 **C 的 stale 判定只比 `head` + `entryCount`**，`tailId` 只作为审计数据记录。
  理由：交互式会话里"压缩跑着的时候用户又敲了一句"是常态，把追加条目判 stale 会把压缩饿死；必须抓到的是并发压缩（head/entryCount 变）或 head 移动。
- 因此语义笔记（`2026-10-21-n4-compaction-semantics.md`）的验收 5 拆成两条：
  - **5a** 并发压缩先提交（head 或 entryCount 变）→ `failed(stale_basis)`，不提交摘要。
  - **5b** 摘要期间只追加条目 → 正常提交，追加的条目仍在上下文里。
